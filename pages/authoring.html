Write an annotation-friendly page

Every page is plain HTML. The annotation overlay attaches to elements that carry data-anchor. There is no framework lock-in.

1The shared shell

Every page is an independent HTML file. The bits that make it part of clickdoc are:

<!DOCTYPE html>
<html lang="en">
<head>
  <meta charset="UTF-8">
  <meta name="viewport" content="width=device-width, initial-scale=1">
  <title>Your page · clickdoc</title>
  <link rel="stylesheet" href="/static/style.css">
</head>
<body>
  <div class="layout">
    <nav class="toc" id="toc">
      <div class="group">Pages</div>
      <a href="/pages/index.html">Index</a>
      <a href="/pages/inbox.html">Inbox</a>
    </nav>
    <main>
      <div class="menu-toggle"><button>☰ Menu</button></div>
      <header class="page">
        <h1 data-anchor="title">Your page</h1>
      </header>

      <!-- your content here -->

    </main>
  </div>
  <script src="/static/nav.js"></script>
  <script src="/static/annotate.js"></script>
</body>
</html>

Rule of thumb. Keep the nav.toc identical across pages so the navigation feels stable. Change only the "On this page" group with anchors to your section IDs.

2Anchors

The annotation overlay attaches a click handler to every [data-anchor] element. The attribute value should be short and unique within the page. Two patterns work well:

Block-level anchor

Tag a whole paragraph, card, or row. The full text becomes the excerpt.

<p data-anchor="hero-tagline">Your stateless agent platform.</p>
<tr data-anchor="cap-virtio"><td><code>hermes-home</code></td><td>...</td></tr>

Snippet-level anchor

Wrap a particular line in a code block when you want comments to target it specifically.

<pre>
foo = 1
<span data-anchor="bar-line">bar = 2  <span class="warn"># fix me</span></span>
baz = 3
</pre>

Stability tip. Anchor ids should describe meaning, not position. data-anchor="step-3" is fragile (you might insert a step 2.5 later). data-anchor="iam-fallback" survives reordering.

3Style components

The shipped CSS gives you a small set of components. Use them; don't bring your own.

Cards

<div class="card" data-anchor="card-x">
  <h3>Title</h3>
  <p>Body...</p>
</div>

Callouts

<div class="callout"><strong>Note.</strong> A neutral pointer.</div>
<div class="callout warn"><strong>Heads up.</strong> Be careful.</div>
<div class="callout red"><strong>Hard rule.</strong> Don't.</div>

Key-value blocks

<div class="kv">
  <div class="k">Field</div><div class="v">Value</div>
</div>

Step flow

<div class="flow">
  <div class="step"><span class="num">1</span><span class="text">Do this</span></div>
</div>

Filesystem tree

<div class="fs-tree">
/path/                    <span class="note">← note</span>
├── <span class="dir">sub/</span>
└── <span class="file">file.ext</span>
</div>

Metrics grid

<div class="metric-grid">
  <div class="metric"><div class="label">Tests</div><div class="value green">286</div></div>
</div>

4Overlaying your content

The bundled pages/ folder is the framework's own welcome screen. To swap in your project:

$ CLICKDOC_PAGES_DIR=$HOME/my-docs/pages python3 server.py

The overlay is checked first for every path under /pages/. If your overlay has index.html, it replaces the welcome. If it doesn't have an api.html, the bundled one wins.

You can mix: keep the bundled authoring.html and api.html reachable while serving your own content for everything else. Just don't put files with the same name in your overlay.

Same logic for CLICKDOC_STATIC_DIR if you need to override CSS or JS — useful for theming.

Recommended layout. Keep the framework as a git submodule or a vendored copy; keep your content in your own repo. Point CLICKDOC_PAGES_DIR at your repo. Updates to clickdoc never touch your content.
